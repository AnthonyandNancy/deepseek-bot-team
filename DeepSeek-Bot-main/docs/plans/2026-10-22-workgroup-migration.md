# 工作群能力迁移到 BotCode

- 日期：2026-10-22
- 状态：需求已决策闭环，待进入实施计划
- 相关：Workgroup-AI 仓库（基线 v0.1.7）；本仓库 v0.2.0

## 为什么

本仓库（DeepSeek-Bot v0.2.0，`ds-bot/` 插件 + `app/` 桌面应用）只有本机多 Bot 的本地群，没有工作群：不能跨用户、跨机器组群，也不能把任务委派给别人的 Bot 团队。

同源的 Workgroup-AI 仓库（DeepSeek-Bot v0.1.7 的 fork）已经做出工作群：`bot-plugin/src/workgroup/`（约 4048 行，client/host/shared 三部分，已在插件入口挂载、可开关）与独立的 `hub/` 服务端，并按 G0–G3 阶段推进（G3 为有条件 PASS，G4 指令已写但未执行）。

三个具体问题：

1. **能力缺口**：本仓库没有工作群。
2. **资产不可直接用**：源仓库的代码与文档都假设 v0.1.7 与「只有 `hub/`、`bot-plugin/` 两个一级目录」；本仓库是 v0.2.0、`ds-bot/`+`app/`，群聊语义已演进（管理员先答/全员轮流、发言顺序、`@` 规则、长任务、Widget 视图）。
3. **交接断点**：进度只存在于源仓库，换仓库即失去「做到哪、下一步做什么」。

## 已定的行为

### 范围与水位

- 交付水位 = 源仓库 **G3**。G4 及之后（Hub 群与消息持久化、升级流程真正生效、跨用户委派与审批闭环、群记忆）不在本次范围内，且不得被声称可用。
- 迁移对象是 **bot 侧**；Hub 保持独立服务端形态，不重写、不并入插件；Hub 代码物理位置放在本仓库（`BotCode` 目录下）。
- 复制基底 = **本仓库 v0.2.0 的群聊代码**；改造目标 = 源工作群行为。两者冲突时以「工作群既有行为」为准，差异逐条记录裁决。
- 历史运行数据不做迁移，由用户手动删除；不写迁移逻辑，也不破坏本仓库既有本地群数据。
- 本次**不发版**：版本号保持 0.2.0，不打包、不发布，验收靠本地运行。

### 可见性

- 工作群入口**保留可见**，并在显著位置标注「本阶段未完成：跨用户群聊与消息尚未提供」；不隐藏、不默认关闭、不假装可用。
- 用户触发 G4 能力时（如跨用户建群、发群消息），必须得到「本阶段尚未提供」的明确结果；不得静默失败，也不得假装成功。

### 隔离与权限

- 本地群与工作群的数据、成员、会话、权限、记忆相互隔离；本地群历史不自动上传。
- 跨用户任务必须由资源所有者本人审批后才执行（规则先立，能力属 G4）。
- 手机号只是登录名，不得宣称「已验证」；无短信 OTP，禁止补回。
- 未登录 Hub 时，本地 Bot 与本地群功能完整可用（沿用源 G3 门禁 5）。

### 验证

- 先跑自动门禁，再交人工验收；顺序不可颠倒。
- AI 不能自证的项（双机实时群聊、观感对照、需要真人判断的交互）标为待人工，不得自评通过。
- 未验证不得写成已实现；模拟不得写成实测；不适用的门禁标「不适用」并给理由，不得标「通过」。

### 文档

- 本仓库文档生效后，Workgroup-AI 文档冻结（只读）；同一规则只在一处定义。
- 文档双轨：设计轨按本仓库约定（`docs/plans/<日期>-<主题>.md`，中文）；实施轨保留源方案的阶段门禁、验收矩阵、缺口登记、每轮交付格式，基线事实全部改为本仓库。
- 文档中的路径、命令、版本、目录必须在本仓库内成立；失效即视为文档缺陷。

### 维护

- 本仓库自此为**独立工作副本**，不再用上游包覆盖；上游更新由维护者通知后人工合并，合并后重跑受影响门禁。

## 不做什么

- G4 及之后：Hub 群/成员/邀请/消息持久化、升级流程真正生效、跨用户委派与审批闭环、群记忆。
- 不重写 Hub 服务端；不迁移历史运行数据。
- 不做工作群 UI 视觉重设计（沿用原版群聊风格）。
- 不重写 Bot Runtime / DSH Agent Loop。
- 不做公网 P2P/NAT 穿透、多 Hub 联邦、多活主节点、跨企业 SSO、移动端全功能客户端。
- 不补短信 OTP；不为桌面端单独做一套工作群实现。
- 不发版、不打包、不发布；本次不处理上游新版本的合并。
- 不顺带重构与工作群无关的既有问题。

## 已知限制

- 交付时工作群**不能跨用户聊天**：Hub 当前没有工作群与消息持久化（G4），工作群只有入口、面板、连接状态、账号与设备管理。
- 桌面应用与插件共用同一份 `ds-bot`（`app` 通过 `file:../ds-bot` 依赖），改动后需重新安装包文件才会带上改动。
- 源仓库遗留缺口随迁移一并继承（例如凭据只做到 0600 文件、不是 OS 钥匙串；手机号未验证属长期决定），需登记，不得在本次顺手改掉。

## 交付物

- 代码：`ds-bot` 内的工作群子系统（G3 水位）+ 位于本仓库的 Hub 服务端。
- 证据：自动门禁重跑结果（条目、结论、证据位置）。
- 文档：设计轨（本文件及后续设计文档）；实施轨（阶段门禁、验收矩阵、缺口登记、进度台账、G4 下一步指令）。
- 清单：人工验收清单（维护者执行）。
- 记录：源文档冻结记录、行为差异裁决记录。

## 核心功能

1. **bot 侧工作群能力迁移**：以 v0.2.0 群聊代码为基底复制出独立工作群子系统，再按源工作群行为改造——群列表与行、群面板、成员与 `@`、消息、轮次与进度、停止、历史、设置、升级入口、Hub 账号与设备入口、审批交互、连接状态与空态。
2. **Hub 作为独立服务端纳入本仓库**：仍为独立进程/独立部署，职责与接口形态不变；bot 适配它，不把它并入插件。
3. **自动门禁重跑**：按源文档要求重跑 G0–G3 可自动化项（构建与生成物一致性、单测、会话身份、双群共存、原版回归、账号与设备、密码认证、撤销即时断线、未登录本地可用等），逐条给结论与证据位置。
4. **人工验收清单**：给出可照做的步骤（做什么、看到什么算通过、看到什么算失败）；AI 不对判断类项目下结论。
5. **文档双轨**：设计轨 + 实施轨（见上）。
6. **未完成状态的显式呈现**：入口可见 + 明确标注。
7. **桌面端形态继承**：工作群以与 bot 相同的方式出现在桌面应用内，不新增第二套窗口或入口。
8. **真相交接与源文档冻结**。
9. **历史数据不迁移**。
10. **独立工作副本的上游合并约定**。

## 状态与生命周期

### 本次迁移工作

```text
未开始
↓ 复制迁移（0.2.0 群聊代码为基底）
已迁移（本地可运行）
↓ 自动门禁重跑
自动项全绿（人工项待办）
↓ 文档生效 + 源文档冻结
可交付
↓ 人工验收清单移交
交付完成（G3 水位）
↓ 维护者回填人工结果
人工通过 → 关闭；有退回项 → 回到"已迁移"修正
```

- 禁止：未运行就宣称已迁移；自动项未绿就交人工；人工清单未成文就宣称交付完成。
- 回退：迁移导致既有行为变化 → 回滚并登记阻塞。

### 门禁状态

```text
未执行 → 通过 / 不通过 / 阻塞（缺条件）/ 不适用
```

- 「不适用」必须给理由；「阻塞」必须写「缺什么、谁能解」。

### 工作群功能生命周期（交付水位）

```text
可用：入口（含未完成标注）、群面板与空态、连接状态、Hub 账号与设备、本地功能不受影响
不可用（G4）：创建真正跨用户的工作群、群消息收发、升级后生效、跨用户委派与审批闭环、群记忆
```

不存在「半可用却对外称可用」的中间态。

### 文档状态

```text
源方案（旧基线，生效中）
↓ 本仓库版草案
草案
↓ 评审通过
本仓库版生效
↓ 冻结源文档
单一真相
```

- **迁移清单**：迁入的能力/文件、未迁项与原因。

- **行为差异清单**：基底与源工作群不一致的每一处及裁决结果。

- **人工验收清单**：步骤、期望结果、失败判据、执行人与结果。
- **进度台账**：阶段、状态、阻塞原因、决定人与日期。
- **已知缺口登记**：是什么、为什么现在不做、谁决定、何时回看。

- **冻结记录**：范围、时点、后续变更落点。
- **不迁移声明**：历史数据处理方式。

## 关联业务

后续制定技术方案时必须检查：

- **群与 Bot**：本地群全部交互（群列表、未读、右键、设置、管理员先答/轮流、发言顺序、`@` 与 `@all`、PASS、每轮上限、长任务与进度、停止）；私聊、Bot 身份、Main Bot 与群管理员权限。
- **入口与界面**：设置页（工作群/账号/连接状态）；DSH 侧栏入口唯一性与位置；工作群「未完成」标注的位置与措辞；桌面应用窗口、导入流程、数据目录隔离、包文件重装。
- **运行时与数据**：会话身份与生命周期、重启/压缩/中断恢复；工具审批 vs 跨用户授权（不可混同）；私人记忆/群记忆隔离；附件、在线状态、已读未读（跨用户部分属 G4）。
- **服务与可靠性**：Hub 的部署、TLS、账号与设备、撤销踢线、日志脱敏、限流；断线提示与重连提示。
- **工程与发布**：`client.js` 构建与生成物一致性检查；版本一致性检查（不发版也必须过）；双语文档、plans 模板、known-issues、release checklist 不被破坏；上游合并流程。

## 边界情况

1. 半成品被误判为故障：入口在但不能跨用户聊天 → 靠显式标注化解。
2. 基底语义差异：v0.2.0 的群规则与工作群既有行为不一致，改造时容易顺手改掉。
3. Hub 与 bot 版本错配：bot 侧可能期望 Hub 尚未提供的能力。
4. 自动门禁跑不起来（环境缺失）：DSH harness、TLS 自签证书、双设备模拟等条件缺失，需与「跑失败」区分。
5. 人工项无法自动替代：真实双机、安装包形态、观感对照。
6. 历史数据残留：手动删除不彻底时旧数据与新手数据并存。
7. 上游更新冲突：独立副本后，上游改动与工作群改造可能撞车。
8. 桌面端未重装包文件：改动已在源码但应用仍跑旧副本。
9. 中断：迁移或文档只完成一半，形成半旧半新状态。

## 异常行为

| 情况 | 用户/接手者应看到 | 系统应保持 |
|---|---|---|
| 未登录/未连接 Hub | 明确的连接状态与原因 | 本地群照常可用，不静默失败 |
| Hub 不可达 | 失败提示与重试方式 | 不丢本机数据 |
| 触发 G4 能力 | 「本阶段尚未提供」 | 不假装成功、不静默丢消息 |
| 迁移导致本地群行为变化 | 影响范围说明 | 回滚并登记阻塞 |
| 自动门禁跑不起来 | 记为「阻塞/缺条件」并说明缺什么 | 不记为通过，也不记为失败 |
| 人工项未执行 | 明确待办 | 不写成通过 |
| 旧数据未清理干净 | 数据来源冲突提示 | 不自动合并、不静默覆盖 |
| 文档路径/命令失效 | 视为文档缺陷 | 修正文档，不以「大致可用」带过 |
| 上游更新与改造冲突 | 冲突范围与受影响门禁 | 不静默覆盖，合并后重跑受影响项 |

## 保持不变

1. 本地群行为完全不变：回答方式、发言顺序、`@` 规则、PASS、轮次上限、长任务与进度、设置、右键、未读。
2. 私聊、Bot 身份、Main Bot 权限不变。
3. 未使用工作群的用户零感知：不登录 Hub 时功能与性能不受影响。
4. 数据边界不变：不读取、不上传用户 DSH 数据、本地群历史、私人记忆、工作目录。
5. DSH 不被修改；缺能力时停下说明。
6. Hub 形态不变：独立服务端，不并入插件进程。
7. 桌面应用既有行为不变：启动、数据目录、导入团队照旧。
8. 工程与发布约束不变：生成物由源码构建、版本一致性检查、双语文档与发布清单。
9. 版本号不变：本次不发布，不触发 Release 流程。

## 验收标准

1. **迁移落地可运行**：本地启动 bot 后，本地群、私聊、设置全部可用；工作群入口按已定方案呈现。
2. **工作群 G3 能力与源一致**：打开工作群能看到未完成标注、群面板与空态、连接状态、账号与设备入口；其余操作以「在源仓库与本仓库执行同一操作、结果一致」判定，不额外假设 G4 能力可用。
3. **G4 能力不被冒充**：触发跨用户建群或收发群消息时，得到「本阶段尚未提供」的明确结果；界面文案与文档一致。
4. **行为与源工作群一致**：同一操作序列（建群、改名、成员、`@`、发言、停止、设置）在两边结果一致；差异逐条列出并说明裁决理由。
5. **本地群零回退**：回答方式、发言顺序、`@` 规则、长任务、设置、未读与迁移前一致。
6. **自动门禁全绿且有证据**：G0–G3 可自动化项在本仓库均有证据；不适用项标注理由；无一项自评通过。
7. **人工清单可独立使用**：每条都有「怎么做、看到什么算通过、看到什么算失败」，执行人无需再问；AI 未对判断类项目下结论。
8. **文档双轨且自洽**：设计轨符合本仓库模板，实施轨保留门禁/验收/缺口结构；路径、命令、版本、Hub 位置在本仓库内全部成立。
9. **续接可用**：没读过源仓库的实施者只读本仓库文档，能说出当前水位（G3）、下一步（G4）、缺口与待决策项，并能按指令开始 G4。
10. **真相唯一**：工作群规则只在本仓库文档定义；源文档标记冻结且不再被当作依据。
11. **桌面端一致且未发版**：工作群以与 bot 相同方式出现；无第二套窗口或入口；`ds-bot` 与 `app` 仍为 0.2.0、一致性检查通过；未产生发布包或版本变更。
12. **数据边界成立**：不读取旧版本运行数据、不执行迁移逻辑；本仓库既有本地群数据不受影响。
13. **隔离与权限规则可验证**：「本地群/工作群数据与会话隔离」「本地群历史不自动上传」「跨用户任务须本人审批」「手机号未验证不得称为已验证」均以可验证条目存在，且当前实现没有违反。
14. **上游合并约定成文**：写明「本仓库为独立副本、上游更新人工合并、合并后需重跑哪些门禁」。
15. **非目标未被扩大**：未包含 G4 能力、Hub 重写、历史数据迁移、UI 重设计、短信 OTP、桌面专属实现、发版动作。
