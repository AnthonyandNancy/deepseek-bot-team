# G2 人工验证清单

这份清单只列**我作为自动化测试做不到**的事。凡是能用 `npm run verify` 证明的，都不在这里——已经证明了（763 passed / 0 failed）。

原因很简单：插件是按 `link:` 装的，源码改了磁盘上可见，但**已加载的 ESM 不热重载**。所以下面每一条都必须在真实 DSH Desktop 里跑，而且**必须先完整重启**。

---

## 0. 前置：必须彻底重启（这一步做错，后面全是白费）

上一轮就是没重启，把旧代码的失败误判成"修复无效"，浪费了一整轮。

**Windows：**

```powershell
# 1. 完全退出 DSH Desktop（托盘也要退）
# 2. 确认一个进程都不剩——必须输出为空
Get-Process | Where-Object { $_.ProcessName -like '*DeepSeek*' }
```

第 2 步输出为空之后再启动 DSH Desktop。

**启动后先确认加载的是新代码**，在插件目录跑：

```bash
cd <repo>/ds-bot && ls -l --time-style=full-iso client.js
```

然后对比 DSH 进程的启动时间（任务管理器 → 详细信息 → 启动时间）。**启动时间必须晚于 `client.js` 的修改时间**。不满足就说明跑的仍是旧代码，后面的观察全部作废。

---

## 0.5 【这次修的就是这两个】右键菜单的重命名与删除

你报的两个问题（重命名提示找不到该群、删除提示找不到该群）已修，**必须重启后**验证：

1. 在侧栏**右键**工作群 → 「Rename group」 → 输入新名字 → 回车
   - **预期**：改名成功，侧栏立刻更新
   - **之前的错误**：`找不到这个群聊`
2. 右键 → 「Delete group」
   - **预期**：该工作群消失；如果它当时是打开的，面板回到空
   - **之前的错误**：`找不到这个群聊`
3. 顺手验证菜单里另外三项（之前同样坏）：**Pin**、**Mark as Unread**、**Hide from sidebar**
   - **预期**：都能生效，且**重启 DSH 后 pin / hidden 状态还在**
   - **之前的错误**：`找不到这个对话`
4. 确认工作群行的菜单里**没有**「Upgrade to a workgroup」（工作群没地方可升），但有「Workgroup settings」
5. **对照**：本地群的右键菜单必须**和以前完全一样**——有「Upgrade to a workgroup」、有「Group settings」、重命名和删除都正常

> 这五项是同一个根因：右键菜单是原版菜单，它调用的是本地群的动作。G1 把侧栏行、面板、输入框都接到了工作群路由，唯独漏了右键菜单。

## 0.6 【也是这次修的】工作群的群设置，每一项都要能写进去

你报的「群设置、菜单等等设置全部无法写入，都是提示找不到这跟群聊」已修。**同样必须重启后**验证。

打开方式二选一（两条都要试，它们本来是两条代码路径）：
- 点开工作群 → 右上角齿轮（信息抽屉）→ 齿轮进入 **群设置**
- 设置 → **Group chats** → 点工作群那一行

逐项改，每改一项都**关掉再打开一次**看是否还在（关键：之前的失败是"看起来保存了、其实没写"）：

1. **Name** → 改名。预期：侧栏、面板标题、抽屉标题都跟着变
2. **Notice** → 写一句群公告。预期：抽屉概览里出现这段公告
3. **Who answers** → 从 Admin leads 切到 Everyone。预期：**重新打开后仍是 Everyone**（这一项之前完全没有处理器，切了等于没切）
4. **Working folder** → 选一个文件夹。预期：重开后还在；且该群成员的对话确实在那个目录下工作（这一项之前写进记录但从未被使用）
5. **Permissions** → 打开「Same for every member」→ 选一个预设。预期：重开后仍是同一个预设
6. **Members** → 「Add member」加一个 Bot。预期：成员数 +1，**且这个成员真的在群里的成员列表里**（之前会画出"已添加"但那行是假的）
7. **Members** → 「Make admin」换人。预期：管理员标签跟着换
8. **Members** → 移除一个成员（× 按钮）。预期：成员数 −1
9. **Sidebar** → Pin / Hide 两个开关。预期：生效，且重启 DSH 后仍在
10. **Manage** → Delete group（点两次确认）。预期：群被删除

**对照（同样重要）**：拿一个**本地群**把这 10 项也走一遍，表现必须完全一致。设置界面是两个域共用的同一份原版代码，这次修复刻意没有碰它——如果本地群有任何一项与以前不同，说明我改坏了对本地群的影响。

> 这一组是 0.5 的延续：0.5 修的是右键菜单那两条，这次修的是设置面上**其余全部**写入。同一个根因——工作群原版设置组件找得到、渲染得出，但它调用的写动作只认本地群。修复放在动作层（按 id 所属域分流），所以设置界面本身仍与原版逐字节相同。

## 0.7 【这次修的】@ 显示的名字、以及删掉的群还在 @ 里

你报的两条（@ 时群名不对、右键删掉的群还出现在 @ 里）已修。**必须重启后**验证。

1. 建一个工作群（先不起名，让它按成员自动命名，例如「You, Chief, 阿三大苏打」）
2. 在**别的对话**里输入 `@` → 展开「对话」分类
   - **预期**：**看不到**任何工作群。工作群是群，不是可引用的一对一对话
   - **之前的错误**：工作群以创建时的 Session 标题出现在这里
3. 把工作群改名为「阿松大」
   - **预期**：侧栏、面板标题、抽屉标题都是「阿松大」
   - **之前的错误**：群记录改了，群的 Session 标题没跟着改，@ 里仍显示旧标题
4. 改名后再 `@` 一次 → 「对话」里仍然**没有**该工作群
5. 右键删掉一个工作群 → 再去 `@` 查「对话」
   - **预期**：该群不再出现
   - **之前的错误**：群的 Session 没被归档，一直留在列表里
6. **重点**：如果这个群是你**在升级前**就删掉的，重启后第一次读 `state` 会自动清掉遗留。重启后直接看 @ 列表即可，不需要你再删一次

对照：本地群同样不应出现在 @ 的「对话」里；本地群改名后，@ 的「对话」里也不应出现旧名。

> 这两条是同一个遗漏：工作群是一个 Session（和本地群一样），但复制时漏掉了原版保持两者同步的两步——改群名时同步 Session 标题（`retitleRoom`），删群时归档群自己的 Session（`deleteRoom`）。

## 0.8 【这轮新发现的】工作群成员卡在审批上

**这条是 G2 门禁原文点名要求、但此前完全没测过的一项**，实测确认是真故障：工作群成员触发需要审批的操作时，请求交给了 DSH 自己的审批卡片，而成员 Session 是隐藏的，卡片无处显示，于是**该回合一直等下去，既没有报错也没有结果**。

1. 建一个工作群，成员选一个权限为「Read only」或需要审批的 Bot
2. 在群里让它做一件需要审批的事（例如写文件）
3. **预期**：群聊里出现可回答的审批（允许/拒绝），你答完它就继续
4. **之前的错误**：什么都不发生，回合永远挂着
5. 答「拒绝」→ 预期它被告知被拒并继续/结束，而不是卡死

对照：本地群里同样操作，审批卡片一直是对的。两边表现应当一致。

> 根因：审批钩子只查了两个原版索引（`groupOwners`/`chatOwners`），工作群成员的归属记录在它自己的 `sessionOwners` 里，于是被判为"不属于任何群"而让给了 DSH 的隐藏卡片。

## 1. 【最重要】身份 prompt 不能重复出现

**这轮刚修的就是这个**，也是我认为最可能出问题的一条。

1. 建一个工作群，把「Writer」加进去
2. 在群里 `@Writer 你好`
3. 点开 Writer 在这次工作群回合里的**系统提示词**（或让它自述："复述你收到的身份设定第一段"）
4. **预期**：`# Your identity` 只出现**一次**，内容是 `You are Writer, a Bot on the user's team in DS Bot.`，后面跟着"answering in a workgroup"那句
5. **错误表现**：出现两次 `# Your identity`，或者模型回答里出现"我是 Writer…我是 Writer…"的重复自我介绍

对照：在**本地群**里同样 `@Writer`，它的身份段也应该只有一段。两边表现应当一致。

## 2. 群外 `message_bot` 被拒，且拒绝话术可执行

1. 工作群里 `@Writer`，让它"把这份资料发给 Outsider（不在群里的 Bot）"
2. **预期**：Writer 报告被拒绝，理由是"不在群里，工作留在群里"
3. **重点看**：如果 Writer 是群管理员或是 Main Bot，拒绝话术里**不应该**出现 `update_group` —— 因为工作群用不了这个工具（这轮修的第二个缺陷）
4. 反过来让它"在群里 @Editor 帮个忙"——**预期**：Editor 真的被叫到，在群里回答

> 本地群仍然应该出现 `update_group` 的建议。两边话术不同是**设计如此**。

## 3. 撤权真的生效（门禁点名）

1. 工作群里 `@Writer` 让它读某个文件（假设它此时权限是 `danger-full-access`）
2. 打开设置，把 Writer 的权限改成 `workspace-write`
3. **回到同一个工作群会话**，再 `@Writer` 做同一件事
4. **预期**：被拒（权限已降级）

**关键**：是**同一个已存在的**成员 Session，不是新建的群。新群会走 S2 的初始化路径，不能证明"撤权传播"（S3）。

## 4. MCP 未批准时确实挂不上

1. 给 Writer 配一个 **stdio MCP**，但**不要**点批准
2. 工作群里 `@Writer` 让它用那个 MCP 的工具
3. **预期**：用不了，且能力状态显示 `needs-approval`
4. 到设置里批准它，再 `@Writer` 一次
5. **预期**：这次能用

> 这条是我最担心真机会有偏差的一条：单测里我给了 Agent 一个最小 `ctx`，真机的 `agent/created` 时序可能不一样。

1. 让某个 Bot 在工作群里做一件长活（比如整理一份大文件）

## 9. 明确**不要**抱期待的两件事

这两项我在此说明，避免你白费时间：

| 项 | 现状 |

| **Session Part（长会话分段 / 压缩 / 回合中换目录）** | **工作群成员拿不到**。原版 `parts.js` 的每个 part 决策都以 `isBotSession` 为闸门，而本域为守住 P0-3 刻意不应答它（应答了原版 turn 机制就会接管本域回合，G1 期间正是这个坑让每个回合变空消息）。已写进审计 §5 注 E，归属 G4。**所以不要期待工作群里长会话会自动分段** |
