## G4-1 两台真机实时群聊（门禁 1）

自动化替身已存在（`ws-events.test.js` + `workgroup-bridge.test.js`），但替身**不能**代替本条。

1. **准备**：一台 Hub（`cd hub && HUB_ALLOW_INSECURE_LOCALHOST=1 npm start`，或配好 TLS 后 `npm start`）；两台机器各自装好桌面端；各注册一个不同手机号的账号。
2. **建群**：A 机器上创建工作群「联调」，在成员区用 B 的手机号邀请。
3. **接受**：B 机器上打开 Bot 面板 → 邀请列表出现该群 → 接受。
4. **聊天**：A 发「一」，B 发「二」，A 再发「三」。
   - **算通过**：两台看到的顺序都是 一→二→三；每条消息旁有 Hub 标记（`· Hub`）；发送方自己的消息不重复出现两次；成员列表两台一致；顶部 Hub 线显示「已连接」。
   - **算失败**：任一台缺消息、顺序不同、出现重复、成员列表不一致。
5. **断网**：B 断开网络（拔网线或关 Wi-Fi），A 连发两条；B 恢复网络。
   - **算通过**：B 恢复后自动补上那两条，且没有重复；B 离线期间自己发的消息显示「等待 Hub 确认」，联网后消失。
   - **算失败**：补不上、补重、B 的消息丢失。
6. **附件**：A 发一张 PNG。
   - **算通过**：B 看到同一文件、能下载、字节一致（可比对文件大小与哈希）。
   - **算失败**：B 看不到、下载失败、文件损坏。

## G3 沿用项

### 1. 插件形态：工作群入口与面板

- **怎么做**：在本机启动 DSH（或 `npx @deepseek-ai/dsh web`），启用 ds-bot，打开 Bot 界面。
- **算通过**：侧栏出现「Bot」入口；进入后能看到工作群面板与空态。
- **注**：G3 时面板顶部有「未完成：工作群聊天与消息尚未提供」的声明；**G4 已移除**，现在改为显示 Hub 连接状态（见 G4-5）。

### 2. 本地群零回退

- **怎么做**：用两个 Bot 建一个本地群，发一条不 `@` 的消息，再 `@` 其中一个；观察谁回答、顺序、底部卡片；停止一次回合。
- **算通过**：与迁移前的行为一致（管理员先答或全员轮流、发言顺序、`@` 只叫被点名者、停止生效）。
- **算失败**：任何一项行为与升级前不同，或本地群列表里混入工作群。

### 3. 工作群行与原版群行并存

- **怎么做**：创建一个工作群（若 Hub 未配置，先看第 4 条）。
- **算通过**：侧栏列表里工作群行与本地群行混排、样式一致、悬停显示完整名称；右键菜单有「Workgroup settings / Rename group / Delete」，本地群右键多出「Upgrade to a workgroup」。

### 4. 未登录时本地可用

- **怎么做**：不登录 Hub，只用本地团队。
- **算通过**：Chief、Bots、私聊、本地群全部可用；工作群面板能打开并提示未登录；没有任何 Hub 报错弹窗。

### 5. 升级后的原群

- **怎么做**：把一个本地群右键升级为工作群。
- **算通过**：原群仍在列表里、点开仍能看到历史、输入框显示只读提示；新工作群出现在列表里；`state.json` 里原群记录未丢失。
- **算失败**：原群被删除或被清空；历史消失。

# 多机联调步骤（2026-10-23 改写）

入口与规则这一轮变了，旧步骤不再适用。

## 前置

| 项 | 说明 |
|---|---|
| Hub 绑定 | 同一局域网要连，Hub 必须监听 `0.0.0.0`：`HUB_ALLOW_INSECURE_LOCALHOST=1 HUB_ALLOW_PLAINTEXT_LAN=1 HUB_HOST=0.0.0.0 npm start`。**两个开关缺一不可**：只设前者仍然只听 `127.0.0.1`（局域网连不上），只设后者会直接启动失败；未设 `HUB_ALLOW_PLAINTEXT_LAN` 也不会像旧版本那样静默改回 `127.0.0.1`，而是启动报错。若配了 TLS 证书则两个开关都不需要。详见 `hub/README.md` 的「Serving the LAN」一节 |
| 两台机器 | A 与 B，都能访问 Hub 的局域网地址（不是 `127.0.0.1`） |
| 两个账号 | 不同手机号。**B 必须在同一 Hub 上先注册**，否则 A 邀请时会得到 `workgroup/invitee-unknown` |
| 登录 | 两台都先在「设置 → Hub 账号」登录。**未登录不能建工作群**（会提示先登录） |

## 步骤

1. **A 建工作群**：登录后「新建 → 创建工作群」。建成的群**已经在 Hub 上**，这是后面的前提。
2. **A 邀请 B**：打开该群 → 右上齿轮 →「群设置」→ 成员卡 →「**添加成员**」下方的「**邀请同事**」→ 填 B 的手机号或 Hub 用户 ID → 邀请。
   - 成功会显示打码手机号（如 `+86****9000`）。
   - 若显示「请先登录 Hub」，说明这台机器还没登录 —— 控件不会消失，只会被禁用并写明原因。
3. **B 接受**：登录后，Bot 面板顶部出现「邀请」区 → 点「加入」。
4. **双向聊天**：两边互发消息与附件，确认顺序一致、发送方能看到自己的消息。
5. **跨用户任务（G5）**：A 在群里向 B 派任务；B 打开该群 → 齿轮 →「群设置」，成员卡下方出现「**等你处理**」审批卡 → 批准并开始 → B 的机器上出现任务 Session 与工具调用，A 的机器上没有。

## 判据

- 第 2 步能看到「邀请同事」控件本身，无论登录与否 —— 这是本轮修的缺陷，**控件不再有条件隐藏**。
- 第 4 步两边的消息顺序一致。
- 第 5 步执行只发生在 B 的机器上（门禁 2 的真机一半）。

# G5 人工项

三条，都是自动化证明不了的那部分。每条都要记录：环境与版本、步骤、期待值、实际值、日志/截图、结论（PASS/FAIL/BLOCKED）。

## G5-T12 批准后确实在 B 的机器上运行（方案 §14 G5 门禁 2 的真机一半）

- **为什么只能人工**：自动化能在同一台机器上起两个域，证明「B 本机建了任务 Session、装上了 guard、Bot 是 B 的名册里的那个」；但「模型调用发生在 B 的物理机器、用的是 B 的账号」只有两台机器才能看。
- **准备**：两台机器各装 DSH + ds-bot，登录同一个 Hub 的两个不同账号（A、B），互相邀请进同一个工作群。
- **怎么做**：
  1. 在 A 的机器上进入该工作群，向 B 的 Chief 发一个任务请求（`task-request`，标题写清楚要做什么）。
  2. 在 B 的机器上打开 Bot 面板，确认出现「等你处理」卡片，卡片上有请求人和请求范围。
  3. 在 B 上选「用已有的 Bot」，点批准；再点开始。
  4. 观察 B 的机器：该 Bot 的 Session 列表里出现一个任务 Session，其工具调用逐步出现。
  5. 同时观察 A 的机器：时间线出现「请求 → 批准 → 运行中」，但 **A 的机器上没有该 Bot 的任务 Session**，A 的模型用量也没有增加。
- **算通过**：执行只在 B 出现；A 侧只有时间线。
- **算失败**：A 侧出现任务 Session，或 B 侧批准后什么都没发生。

## G5-N3 任务交互与原版对照无明显违和（方案 §15 T19 同类）

- **为什么只能人工**：「无明显违和」是审美判断，写不进断言。**本项不写 PASS 的自动化替代，也不代维护者确认。**
- **怎么做**：并排看两屏——一屏是原版本地群的群聊，一屏是工作群里出现了审批卡之后的群聊。
  - 审批卡的字体、行高、圆角、间距是否与群成员/邀请行一致
  - 「批准 / 拒绝」按钮是否与「加入 / 拒绝」邀请按钮同一视觉层级
  - 下拉选择（用哪个 Bot）是否与设置里的下拉一致
  - 卡片出现后，群聊区是否被挤压得不适
  - 深色主题下是否仍然可读
- **算通过**：以上五项无人为突兀，与 G4 已确认的群聊观感连续。
- **记录方式**：截图对比 + 一句结论。**没有截图不算通过。**

## G5-T14 符号链接指向批准目录之外必须被拒（§15 T14 未自动覆盖的部分）

- **为什么还要人工**：判定逻辑已经自动化并通过（`decide` 与 `verifyBeforeRun` 两侧都 `rt.real`，`a run whose Session works outside the approved folder is refused` 用 `rt.sessionFolder` 报告的真实 cwd 触发了同一条判定）。剩下的是**在真实文件系统上真的建一个符号链接**、让 DSH 把真实 Session 办到那里——同一逻辑在真机上的复现，不是新逻辑。
- **怎么做**（在 B 的机器上）：
  1. 建一个批准目录 `approved/`，以及目录外的 `secret/`，里面放一个文件。
  2. 在 `approved/` 里建一个指向 `secret/` 的符号链接（Windows 用 `mklink /D`，需要开发者模式或管理员）。
  3. 批准一个任务，把 workDir 指向 `approved/link`（即那个符号链接）。
  4. 让任务尝试读 `secret/` 里的文件。
- **当前预期**：拒绝理由明确指向越界（`task/bad-workspace`），且不回退到团队目录。
- **算通过（补齐后）**：拒绝理由明确指向越界，且**没有回退到团队目录**。
- **算失败**：读到了文件，或悄悄换成了团队目录继续跑。
